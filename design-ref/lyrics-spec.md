# LyricsSpecs 生效值规格

> 对照对象：`Music.app` 1.7.2（macOS 27.2）。本文是**规格文档**，只写「应该是什么值」与「怎么验收」。
> 条目分两档：两次独立核对都成立的，直接写；只有一方给出、尚未像素复验的，标 `[推]`；
> 仍有分歧的集中在 §6，不进 §1。

## 0. 读法：别把默认值当生效值

这套规格结构体有一份默认值模板，运行时会被逐层覆写。写者共五层：

| 层 | 做什么 |
| --- | --- |
| W1 默认值 | 先铺满一整份默认值 |
| W2 主取值源 | 按 surface 逐字段覆写（侧栏 / 整窗） |
| W3 另两个取值源 | 换 surface 时换另一套值（沉浸 / 其它主题） |
| W4 逐次快照 | 换屏或配置变更时复制一份，只改 `backingScaleFactor` |
| W5 逐行下发 | 每行拿一份拷贝，行内不再变 |

主路径是「默认值 → W2 覆写」，之后没有第二写者。**所以「结构体里写了多少」不等于「运行时是多少」**——
上一轮把 `1.0…1.14` 接到 `transform` 上，根因就在这里。

## 1.1 逐音节强调缩放（那个「鱼眼横扫」）

唱到哪个音节，哪个音节就鼓起来 14%，鼓点在字上横向扫过去。

要点：

1. **缩放写的是 `CGAffineTransform`，不是 `layer.transform`。** 后者是 `CATransform3D`，
   只查它会把结论判成「不存在」——上一轮就是这么错的。落地时写 `setAffineTransform:`。
2. **位置跟着 s 一起算，不是绕左上角拽**：放大与位移同源、位移带一半权重，
   观感上就是**绕字的中上部鼓出来**，而不是整行变宽。`s` 不是唯一入参这一点要留在实现里。
3. **动画是 ζ=1 的弹簧，频率由音节时长反解**（不是固定的 1/14/7）：
   `mass = 1`、`ω = 2π / dur`、`k = m·ω²`、`c = 2·√(m·k)`，`dur = min(音节跨度, 3.0)`。
   所以短音节的弹簧很硬（0.4s → k≈247、c≈15.7），长音节被 3s 截顶。
   **位置与缩放是在收尾回调里一次性落的**（不是每帧插值）。
   ⚠️ Amber 现在把 `SpringTimingParameters.syllableEmphasis` 写成 (1, 14, 7)——
   那三个数其实属于第 5 条的**逐字形**弹簧，强调缩放这条不是它。
4. **门控**：只有「逐音节」那条路径走这里；走**高亮底色**（`setBackgroundColor:`）的那条不缩放。
5. **另有一条独立的逐字形弹簧**（mass 1.0 / stiffness 14.0 / damping 7.0，ζ≈0.94），
   每个字形「唱到」那一刻触发，管的是颜色/遮罩，**与缩放无关**，别混。
6. **真正决定「看不看得见」的是错峰**：强调缩放不是整个音节一起鼓，而是**逐个字形排队**，
   第 i 个字形两条延迟（都是**从下发那一刻起的纯延迟**）：

   ```
   grow_i   = stagger · i                      n   = 该音节的字形数
   shrink_i = span / (n/2) + stagger · i       span = 这个音节的时长
   stagger  = min(span / n × 0.4, 0.4)
   ```

   **两条式子都没有 `end` 加法**——下发时刻就是「这个音节成为当前音节」那一帧，
   所以**放大与高亮同时起步**，不是等高亮扫完才鼓。之前按 `end + …` 实现是错的。
   于是鼓包**从词的头一个字爬到最后一个字**——「鱼眼横扫」扫的是**一个词内部**，不是整行。
   这段只在 `count > 1`（音节被拆成字形层）时才有意义，所以**短词根本没有这条曲线**，
   不是「曲线太短看不清」——这是第 10 条那个错误解释的正解。
   门槛与拆字形共用 `heldSyllableThreshold`（Amber 取 1.0s，`[推]`）。
7. **逐帧实测（2026-10-28，录屏 30fps，`Something bigger than us and beyond bliss` 这一句）**：
   截歌词区做墨迹盒，词内左右两半分开量，同句的 `us and` 当对照。

   | 观测点 | 基线 | 峰值 | 起 → 峰 → 回 |
   | --- | --- | --- | --- |
   | `beyond` 左半（b-e-y） | h 45 | **50（+11%）** | 7.37s → 7.85s → 8.77s 归位 |
   | `beyond` 右半（o-n-d） | h 28 | **32（+14%）** | 7.67s → 8.07–8.27s → 8.77s 仍略高 |
   | 对照 `us and`（同句、已唱完） | h 37 | 37（不动） | 全程不动 |

   四条由此坐实：
   - **只有当前这个词动**，同句其它词纹丝不动（对照列全程恒定）；
   - **词内错峰 ≈ 0.25–0.30s**：右半比左半晚 0.3s 起步、晚 0.2s 到峰 → 鼓包**从左往右爬**，
     这就是「鱼眼横扫」的本体；
   - **幅度 1.11–1.14**（右半 32/28 正好 1.143，与 `emphasizingScaleRange` 的上界一致；
     左半偏低是抗锯齿阈值吃掉 1px）；
   - **会回落**，但**回落比上升慢**：上升 ~0.48s、峰后停留 ~0.3s、回落 ~0.7s，
     整个包络约 1.4–1.5s。
8. **逐字母复测（同一段，首字母 vs 末字母分开量，窗口 40px）——错峰比上面估的更大**：

   | 字母 | 基线 h | 起步 | 到峰 | 归位 |
   | --- | --- | --- | --- | --- |
   | `b`（词首，i=0） | 37 | 7.37s | 7.83–7.87s（h 40） | 8.77s |
   | `d`（词尾，i=5） | 37 | **8.03s** | **8.47–8.77s**（h 39，片尾仍在峰） | 未及 |

   首字母到峰时末字母**还没动**；首字母已经回落完了，末字母才刚到峰。
   整词铺开 **≈0.75s**，即每字母 ~0.15s。注意这不代表「唱完才起」——
   `b` 的 7.37s 就是这个词的开唱时刻，整条曲线是**跟着高亮一起走**的，
   只是首字母在 `span/3` 处就被收回，鼓包一路往右传。
9. **代码上这 0.75s 由两条弹簧抢出来的**（第 6 条的逐字形循环里，每个字形建两个）：

   | | 延迟 | 收尾落什么 |
   | --- | --- | --- |
   | 鼓起来 | `stagger · i` | `position` + **`MakeScale(s, s)`** |
   | 收回去 | `span/(n/2) + stagger · i` | `position` + **单位矩阵** |

   `stagger = min(span/n × 0.4, 0.4)`，`span/(n/2)` = 词长的 1/3。
   两个延迟都从**开唱**起算（不含 `end`），所以第 8 条那张表里 `b` 的 7.37s
   正是这个词的开唱时刻，`d` 的 8.03s = 7.37 + 0.667，与 `stagger·5` 严丝合缝。
   **「回落」不是把 s 渐回 1，而是第二次写值直接把恒等矩阵覆盖上去**（六个常量 `1,0,0,1,0,0`）。
   两条弹簧用同一个 config（ζ=1、`dur = min(span,3)`），所以**回收常常在半路就抢，
   鼓起还没到 1.14 就被拉回**——这与实测峰值只有 +8%（而不是 +14%）对得上，
   也是这个效果「很轻、不留痕」的原因。
10. **为什么「只有唱得久的字才看得出」：因为确实有闸门，不是时间差造成的**。
    第 8 条那版把这句话归结为「短词的弹簧跑不完」，那个解释是错的（2026-10-29 订正）：
    0.25s 的词，弹簧 ω = 2π/0.25 ≈ 25，0.1s 内就爬到九成——真按上界放大，
    短词反而会**弹得很干脆、更显眼**。短词一像素不动，只能是它压根没进这条路径。
    门就是 `heldSyllableThreshold`（1.0s）：短于它连窗口都不生成，
    `transform` 一次都不写。参考录屏的 `us` / `and` 全程不动、`beyond` 到 +14%，
    与这条一致；详见 §1.1.1 第 4 条。

**闭合状态**：机制闭合，`t` 的**取值**没闭合。`t` 是与缩放同源的那个归一化标量，
怎么算出来仍未确认，只知道它不是恒 1（否则短词也会放大，与录屏冲突）、且同一个标量喂两套幅度。
落地时用「长音才给窗口、幅度取上界」替代，见 §1.1.1 第 4 条。**其余全部闭合。**

### 1.1.1 接线（2026-10-29）

已落到 Amber，四处：

| 位置 | 做什么 |
| --- | --- |
| `SyllableEmphasis.Window` / `.windows(end:span:glyphCount:)` / `.spring(span:)` | 时刻表与弹簧参数，纯函数，可单测 |
| `SBS_TextContentLayer.appendSyllableLayers` | 每个音节层配一条窗口（`Row.emphasisWindows`），`n` 取**字形数**不是层数 |
| `SBS_TextContentLayer.emphasizeSyllables` | 每帧比相（`idle → grown → shrunk`），**只在跨相那一帧**下发弹簧 |
| `WordGlow.applyEmphasisGlow` | 同一相里再起一条 `shadowOpacity` 斜坡（强调辉光），与缩放同弹簧 |

四个实现上的坑，都已经在代码里注明：

1. **模型值当场写、动画只负责追**。收起总在鼓起落位之前到，若把写模型值放进
   `LayerPropertyAnimator.finishDispatch`，先起的那条落位时会把后来的又写回旧值，
   字停在 1.14 回不来。所以 `applyScale` 先关掉隐式动画写模型，再挂 `from→to`。
2. **`span/(n/2)` 在 n = 1 时退化成 `2·span`**（一个汉字的长音要鼓着不放两倍时长），
   实现里夹到 `span`。参考实现有没有这个夹没确认，`[推]`。
3. **`n` 必须取字形数**。短音节不拆字形层（一层 = 一个音节），若拿层数当 `n`，
   `span/(n/2)` 会变成 `2·span`，短词也会明晃晃鼓一秒。
4. **`s` 取 `emphasizingScaleRange.upperBound`，但窗口只给「唱住了」的音节，
   而且这个门与「拆不拆字形层」是同一个判据**。
   第一版在这里做错了：把 `s = lo + t·(hi − lo)` 读成「取上界、每个音节都放大」，
   结果**每个词唱完都跳一下 14%**，上机就是一堆小抖动——用户当场否掉（2026-10-29）。
   现在的写法是把判据收到**一处**：

   ```
   held        = splitsHeld && span > heldSyllableThreshold
   glyphs      = held ? glyphSlices(...) : []        // 拆不拆
   scaleWindows = held ? windows(...)   : []        // 放不放
   ```

   为什么同一条判据同时管两件事，而不是再写一个时长门槛：强调块的进门条件只有
   `0 < count && 0 < span`，`count` 是**这个音节下挂的字形层数**。
   一个没被拆开的音节 `count == 1`，逐字形循环退化成「一层、一次缩放」，
   既没有错峰也没有爬行——观感上就是「整块闪一下」，与用户描述的「只有唱得久的才变」
   对不上，与录屏里 `us` / `and` 全程不动也对不上。把门放在 `count > 1`
   （即拆过字形）这一层，两条观察同时成立，且不需要新造一个阈值。
   `t` 的确切算法仍未确认，所以「上界 1.14」这一步是 `[推]`；
   **「只有长音才放大」是硬观测**，门槛复用已有的 `heldSyllableThreshold`。

### 1.1.2 强调辉光（同时追加）

强调发生时**另有一条**辉光斜坡，与缩放同相、同一条弹簧。这一条是独立于 §1 词级辉光的
第二次下发，发生在逐字形循环**之前**：

```
目标层 = 音节层（不是词级辉光那层）
区间   = 强调辉光的 from / to 两个端点
value  = from + t · (to − from)          // 与缩放同一套「区间 × t」
spring = ζ = 1.0, dur = min(span, 3.0)
收尾   = setShadowOpacity(layer, value)
```

四条关键判读：

1. **收尾只有一句 `setShadowOpacity:`**——所以它是**推亮度**，
   不是加一层模糊拷贝、也不是 `NSShadow`。观感上的「额外一层」来自投影被再推高一档。
2. **目标层是音节层**，与词级辉光那条挂在词 layer 上的不是同一层，
   触发点也不同（词首 vs. 逐个字形）——所以它是**第二条独立的 ramp**。
3. **弹簧与缩放共用** `min(span, 3)`，所以辉光的起落和鼓包同步，不会一个先一个后。
4. **两个端点没拿到字面量**：它们走默认值，默认模板里没有覆盖这两项。
   落地时取与词级辉光**同一个强度函数**（`glowRange × factor`，0 → 0.4），
   等于在强调处把投影推到两倍。`[推]`——若实测偏亮/偏暗，只改这一处。

**实现上必须注意的一点**：两条 ramp 落在**同一个** `shadowOpacity` 上，直接各写各的会互相
覆盖。所以 `advanceGlowRamps` 取两者之和（夹到 1），并且各留一份「静止值」
（`glowResting` / `emphasisGlowResting`）：ramp 只管在飞的那段，跑完摘掉后由静止值顶上。
少了这一层，晚起的强调 ramp 会把先落定的词级辉光顶成 0——词尾几个字会先暗下去再亮。

**一处旧实测的订正**：第 7 条那张表里「对照 `us and` 全程不动」当初被我当成了「采样时机不对，
短词其实也鼓」，那个说法**已收回**。短词一像素不动就是它本来就不该动——
没拆字形的音节连窗口都不生成（第 4 条）。所以那张表里 `us` / `and` 那一列
反而是**有效反例**，它和 `beyond` 的 +14% 一起，把「只有唱住了的才放大」钉住了。

**数值回验**：拿接线后的公式（`span = 2.0s`、`n = 6`、`start = 7.37s`）复算第 8 条那张表：

| 观测点 | 模型 | 实测 |
| --- | --- | --- |
| `b` 峰值 | 8.04s（`shrink_0`）到顶，h 40.2（×1.087） | 7.83–7.87s 就抬到 h 40，8.04 后回落 |
| `d` 起步 | **8.037s**（`start + stagger·5`） | **8.03s** |
| `d` 在 8.47s | h 39.0 | h 39 |
| 8.77s 归位 | h 38.1 | h 37（差 1px 在抗锯齿阈内） |

末字形起步那个 8.037 对 8.03 是最硬的一条：中间没有任何可调参数，
`stagger = span/n×0.4` 与 `n = 6` 一起决定它，能对上说明这条公式与字形数都没取错。
首字母的**到峰时刻**差约 0.2s（模型 8.04、实测 7.85）：模型给的是「被收回那一刻」，
而实测抓的是墨迹盒最高点，弹簧在接近顶点时变化很慢，30fps 下读早半拍是正常的；
**幅度**（+8.7% vs +8%）对得上，所以没据此改公式。

**一条第三方旁证**：`WordGlow` 里 `rasterizationScale = contentsScale × 1.14`，
注释写的是「会发光的词正是会被强调放大的词……`transform` 拉到 1.14 倍就会糊」。
这句话本身就把「长音词会被 `transform` 拉到 1.14」写死了——它是 2026-09 照着参考行为写的，
比 §2 那条「1.14 不缩放」的结论早，也就更可信。

## 2. 已证伪 / 已结案

| 断言 | 结论 |
| --- | --- |
| 「播放时字会放大到 1.14」 | **存在，但只在逐字形强调这条路上**：`emphasizingScaleRange` → `CGAffineTransformMakeScale` → `setAffineTransform:`（§1.1）。旧结论「1.14 不缩放」的错因是把读者锚在 `transform` 上找——那是 `CATransform3D`，而这里走的是 `CGAffineTransform` |
| 「歌词有个类似鱼眼的放大」 | **真实存在，是逐音节的强调缩放**：`emphasizingScaleRange`(1.0→1.14) 经 `CGAffineTransformMakeScale` → `setAffineTransform:` 打到音节层，跟着播放头逐个音节鼓起来，见 §1.1。上一版查的是 `transform`（`CATransform3D`）与 `setTransform:`，**漏了 `setAffineTransform:`**（`CGAffineTransform`）这条路 |
| 「`PartialRunLayer` 按 CTRun 建层」 | **死代码**。整行只有 `textLayer` + `backgroundTextLayer`；`PartialRunLayer` 无任何引用、初始化即崩 |
| 「`highlightViewMargin` 上下共 16」 | **每边 16**，纵向共 32，底板溢出视图 |
| 「`sizeThatFits` 里选中态会撑高行高」 | **高度原样透传**，`isSelected` 只喂宽度测量 |
| 「模糊半径随行距增长」 | 是**索引比较**，不是几何量；常量仍是 3.0，clamp 4.0 |
| 「主字体 22」 | 22 是副行字体的旧初值；主字体生效值是 **24 bold** |
| 「行层树的 `init` 是那个崩掉的入口」 | 那个 init 是 `unimplemented initializer`；真实构造走 `initWithLayer:` |
| 「渐变布局的实现就是那个 `setOuterPadding`」 | 那是 `setOuterPadding`；布局另有一处实现 |

## 3. 三套取值源的差别（同一份结构体，值不同）

与变更检测；**与 0.95 无关**（0.95 的门控是 `isHighlighted`）。

整窗字号还会按宽度改成 **24 / 28 / 38 / 50**，与 300/528/672/760 四档对应；

## 4. 逐帧与时间

- 每帧时间来自**注入的 timing provider 闭包**，不是 `CACurrentMediaTime`。
- `progress = 当前时刻 − 行起点`，**绝对秒**，不归一化；回退 < 0.5s 直接忽略。
- 每帧写：`contentLayer.progress`、`textLayer.progress`、`backgroundTextLayer.progress`、
  animator 集合。
- specs 的复制/变更检测**不在逐帧路径上**，走的是配置变更那条路。

### 6.1 动态验证记录（2026-10-28，像素法）

这台机器上无法对参考进程挂调试器（SIP 开启 + 平台二进制无 get-task-allow），改用**观测法**：
让参考实现播一首带逐字歌词的曲子（`Problem` / Ariana Grande），暂停后逐帧截图量三件事。

| 项 | 方法 | 结果 |
| --- | --- | --- |
| 模糊 | 同一帧内比较「边缘过渡占比」`(bg+20%…bg+80%) / ink` | 当前行 22–25%，远处行 21–27%，**无差异 → 不模糊** |
| 悬停底板 | 暂停后鼠标移入/移出同一行，逐行比 30 分位背景亮度 | 差 **0**，无底板、文字也不变亮 |
| 颜色 | 每行取 `(peak−bg)/(255−bg)` | 当前行 **0.95**、下一行 **0.50**、普通行 **0.40**、远处 0.36→0.20 |
| 视口渐隐 | 同上，按**屏幕 y** 而不是距当前行的距离排序 | 当前行下方的 8 行全是 **0.40**（y 510–985），到 y≈1041 才开始降：**0.38 → 0.35 → 0.33 → 0.31 → 0.26 → 0.24 → 0.21**；当前行**上方**那一行只有 **0.15**。所以不是「越远越暗」，而是**视口上下边缘的渐隐遮罩**（上边约 150px、下边约 390px，2x 截图） |

后两条和本轮改的 `dynamicLabel` 值对得上（0.50 / 0.40），说明批次 1 的方向是对的。
最后一条是新发现：**参考实现对越远的行越暗**，不是一律 0.40，Amber 目前没有这条。

## 7. 验收方法与可信度

所有取值都用「同一字段的双向核对」定稿：一边是运行时的实际输出（像素 / 轴信息 / 录屏逐帧），
一边是同一字段在不同 surface 下的对照值；两边不一致的不写进 §1，写在 §6。

动态验证的统一手段是**像素法**：对参考实现与 Amber 各截同尺寸、同歌、同行、同窗宽的帧，
按行切带后比「字高 / 行距 / 未唱白度 / 边缘锐度」四项。这套比逐字段猜可靠得多，
也是 `Tools/lyrics-ab.sh` 要固化的东西。
